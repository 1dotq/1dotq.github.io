When Windows Event Logging Goes Dark: MS-EVEN6 Stack Exhaustion and the Telemetry Gap

2026-10-25  —  Windows Event Log / MS-EVEN6  —  VULN-192344
windows event-log rpc security-telemetry
Field Details
Research reference VULN-192344 / MSRC Case 119893
Component Windows Event Log service (wevtsvc.dll)
Relevant interface MS-EVEN6 / EvtRpcRegisterLogQuery
Observed failure Stack exhaustion, STATUS_STACK_OVERFLOW (0xC00000FD), service termination
Vendor disposition Moderate severity; case closed September 29, 2026; no CVE or immediate servicing committed
Public exploit Not provided

Disclosure note: This article documents observed behavior, defensive implications, and the vendor-assessment history. It deliberately omits the proof of concept, crafted request, payload structure, and procedural reproduction instructions. The findings are configuration- and build-dependent; the status of a comprehensive fix is not established here.

Why this matters

Windows Event Log is more than a convenient place to look up errors. It is a core source of audit and operational evidence for endpoint investigations and security monitoring platforms. A service restart may restore the service, but it does not necessarily reconstruct events that were never committed while the service was unavailable.

My research into the MS-EVEN6 remote event logging interface identified a failure mode in which malformed query processing could exhaust a service thread's stack and terminate the Windows Event Log service. In the controlled lab tests, missing events were not recoverable after the Event Log service restarted. The interrupted event stream also produced gaps in telemetry available to a Wazuh deployment.

The important distinction is between service availability and the continuity of security evidence. Those are related, but they are not the same property.

Technical overview

The affected component in my testing was wevtsvc.dll, which supports Windows Event Log operations. The behavior involved the EvtRpcRegisterLogQuery path exposed through the MS-EVEN6 RPC interface. The immediate failure signature was STATUS_STACK_OVERFLOW (0xC00000FD), after which the service terminated and could be restarted by Windows service recovery.

The investigation also raised an authorization-ordering question. In one set of tests, an ordinary query received an access-denied response for a channel, while a malformed query targeted at that channel caused service termination. This is consistent with some query processing occurring before the relevant channel-access decision in that exercised path. It is not, by itself, proof that a caller could read protected log contents or that every account type could exploit the behavior.

Microsoft ultimately characterized the case as an authenticated remote denial of service affecting a single auto-restarting service. Earlier test notes also explored null-session behavior, but authentication and network exposure were not consistently established across all later configurations. I am not representing this as a universally unauthenticated vulnerability.

Test environments and scope

The investigation spanned multiple Windows lab environments, including Windows 11 24H2 and Windows Insider Canary, with supplementary Windows Server testing. Two particularly relevant environments in the retained research notes were:

Lab target Recorded observation Scope limitation
Windows 11 24H2, build 26100.1 Event Log service termination; controlled event-recording comparison This was an early build without subsequent cumulative updates; results must not be generalized to fully updated systems
Windows 11 Insider Canary, build 27924.1000 Event Log failure signature reproduced; system instability observed in some runs Later network/domain changes changed reproducibility; this does not prove a general kernel crash or uniform exposure

The exact behavior depended on the build, authentication context, firewall configuration, and network/domain state. Testing against a domain controller did not establish a reliable non-administrator attack against domain controllers. A later authorization-ordering test also used a UAC-filtered account that belonged to the local Administrators group, so that particular result should not be described as proof of exploitation by a genuinely unprivileged account.

What the evidence showed

1. A service crash rather than ordinary query failure

Windows Error Reporting identified the Windows Event Log service and wevtsvc.dll with an exception code of 0xC00000FD. The service was observed terminating unexpectedly. Service recovery brought the service back in tested cases, but did not undo the interruption.

2. Events missing from a controlled observation window

Finding: events missing during the crash window were not recoverable following service restart in the tested environment. In a controlled Windows 11 Application log comparison, all three synthetic events generated before the interruption were present afterward (3/3 recovered). By contrast, none of the three synthetic events generated during the interruption appeared after the service resumed (0/3 recovered). The missing events were not subsequently backfilled in that observation; restarting the Event Log service did not restore them.

The original MSRC submission separately documented a Security log comparison reporting the same non-recovery pattern after a crash. These are lab-specific observations involving small samples—not proof that every event source, Windows release, or monitoring configuration loses events identically. “Not recoverable” describes the result of the tested restart and log inspection; it does not establish that data could never be reconstructed from an independent source.

Strictly speaking, a record never committed to the event log cannot be described as an existing record later deleted from disk. The concern is audit-record non-creation or non-recovery during interrupted logging, not demonstrated arbitrary deletion of historical event files.

3. Wazuh telemetry reflected the gap

I ran a Wazuh agent on a Windows test host and monitored incoming Windows events while the Event Log service was interrupted. The SIEM view showed an interruption in expected Windows-event telemetry. Microsoft Defender status checks indicated that its antivirus and real-time protection components remained enabled in that test environment, illustrating that endpoint protection status and Windows-event visibility are separate things.

The Wazuh observation establishes a visibility gap in the tested collection path, not that the endpoint was undetected by every possible security product or that all sources of telemetry stopped.

4. A question about the order of authorization and parsing

The same research showed a difference between how the service handled a benign access-denied query and a malformed query that produced a crash. This warrants investigation of the order in which the service validates query structure and evaluates channel permissions. It does not prove unauthorized log reading, arbitrary code execution, or a general security-boundary bypass.

Why automatic restart is an incomplete answer

Microsoft emphasized that the host automatically restarts the affected service. That is an important mitigation against prolonged service unavailability, and a factor in severity assessment.

However, restarting a logging service is not equivalent to proving that no monitoring data was lost. A useful assessment has to ask:

  • Were events generated or buffered during the interruption?
  • Did the source commit those events after the service returned?
  • Did forwarding agents and collection systems detect the outage and recover the gap?
  • Was there independent telemetry available to establish what happened while the primary source was unavailable?

Observed outcome: the Event Log service restarted successfully, but the missing test events were not recoverable from the Windows event log afterward. They did not reappear or backfill during the documented observation. In this test, recovery of the service was therefore not recovery of the audit trail.

Microsoft's September 29 explanation described the issue as authenticated stack exhaustion in the Event Log service, requiring valid network credentials and affecting a service that can automatically restart. MSRC assessed that impact as Moderate and below its immediate-servicing threshold. It offered researcher recognition through its Special Mentions program.

I disagree that service restart alone adequately captures the implications of the event-visibility gaps observed in my lab. Nevertheless, a disagreement about severity is not proof of a hidden patch, an exploitable privilege boundary, or a vulnerability on every current Windows build. I am preserving that distinction here.

As of the correspondence available for this write-up, Microsoft had not issued a CVE for this case, and I do not have confirmation of a complete fix or of a later revised severity decision.

Defensive considerations

Defenders can reduce exposure and improve resilience even when a vendor has not announced a dedicated update:

  1. Limit remote Event Log RPC exposure to explicitly authorized management and collection systems using host firewall and network segmentation controls.
  2. Alert on unexpected Windows Event Log service termination or repeated restarts, using an independent monitoring path where possible.
  3. Measure collection health, not just endpoint health. A functioning EDR or antivirus service does not guarantee that Windows Event Log-derived SIEM data is complete.
  4. Correlate multiple telemetry sources—for example, endpoint telemetry, network monitoring, authentication infrastructure, and collector health signals—to distinguish quiet systems from blind spots.
  5. Test the recovery characteristics of collection pipelines in an authorized lab, including buffering and backfill behavior, rather than assuming restored service means restored evidence.

These measures are risk reductions, not a substitute for a vendor-side fix where a vulnerable code path remains reachable.

Closing thoughts

This investigation began with an Event Log service crash. It became a study of how security visibility behaves when the infrastructure responsible for producing that visibility fails.

MSRC's Moderate-severity assessment and my disagreement about the telemetry consequences are both part of the record. My goal in publishing the research is to make those distinctions clear and to encourage security engineers to assess the continuity—not merely the availability—of their audit pipelines.

When security telemetry goes dark, the absence of an alert does not necessarily mean the absence of a threat.
